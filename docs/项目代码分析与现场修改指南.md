# CampusReserve 项目代码分析与现场修改指南

> 依据当前仓库代码整理，适合答辩前阅读和现场定位。规划目标与已实现功能要分开讲；运行步骤见[答辩操作手册](答辩操作手册.md)，原始需求见[项目规划](project-plan.md)。以下路径均相对项目根目录 `C:\Code\Python\CampusReserve`。

## 1. 三分钟讲清项目

这是一个校园羽毛球场预约系统。学生登录后查看**今天或明天**的场地库存，选择同一天的 1～2 个时段提交预约；每名学生每天累计最多占用 2 个时段，同一时间可以选择两片不同场地。今天已经开始的时段仍展示：已订的显示“已预约”，其余显示“已过期”。管理员可维护场馆、场地、开放模板和例外日期，生成及控制放号批次，查询预约、现场签到和查审计日志。

一次正式预约的链路是：

```text
web/src/App.vue
  → Nginx /api 代理 → FastAPI 预约接口
  → Redis Lua 原子校验库存、额度、幂等并写入 Stream
  → Booking Worker 消费 Stream
  → PostgreSQL 事务再次校验并写入预约、明细、每日用量、状态日志
  → Worker 更新 Redis 请求结果；前端查询结果或从“我的预约”找回
```

`SyncBookingService` 是 Worker 复用的数据库落库与一致性层；对外 `POST /api/v1/booking-requests` 入口先经过 Redis。调度器负责生成今天/明天的库存、到放号时间开放批次、同步 Redis 库存，并归档已结束的预约。Nginx 将请求分到两个 API 实例；两个 Worker 共用一个 Redis Stream 消费组。

**答辩时不要把目标说成已测结果。**“1 万人、峰值 5,000 RPS、0 超卖”是规划中的容量目标。当前 `tests/load/locustfile.py` 只压健康检查；并发一致性有集成测试，但没有由该 Locust 脚本得出的完整预约链路 5,000 RPS 验收报告。

## 2. 代码组织与读法

| 目录 | 职责 | 建议阅读顺序 |
|---|---|---|
| `web/` | Vue 3 + TypeScript 学生和管理员页面 | `App.vue` → `AdminPanel.vue` → `style.css` |
| `apps/` | API、Worker、Scheduler 三种进程入口 | `api/main.py` → `booking_worker/main.py` → `scheduler/main.py` |
| `src/campus_reserve/` | 共享的领域模型、接口、业务服务、数据库/Redis 访问 | 某个 `controllers/http.py` → `schemas.py` → `services/` → `repositories.py` → `infrastructure/` → `models.py` |
| `migrations/` | Alembic 数据库表结构、约束、种子数据变更 | 按 `0001` 至 `0006` 顺序 |
| `tests/` | 单元、数据库/Redis/HTTP 集成和 Locust 示例 | 按老师要求的功能查同名测试 |
| `deploy/`、`compose.yaml` | 容器构建、反向代理、监控 | 部署问题从这里查 |
| `docs/` | 规划、操作及本分析文档 | 先看操作手册，再按需查本文 |

术语：`service_date` 是**场地使用日期**；`release_at` 是放号时间；`release_batch` 是某个使用日期的一批库存；`booking_slot` 是一片场地的一个 60 分钟时段；`request_id` 是客户端生成、用于安全重试和结果找回的 UUID；`booking_no` 是确认预约后生成的业务编号，前面的日期来自使用日期。

### 数据一致性可这样解释

1. **Redis 先防抢占冲突**：Lua 在单次原子调用里读取库存、核对每日额度、写占位和 Stream 事件，同一时段不会被两个请求同时抢到。
2. **Worker 再做数据库校验**：数据库事务锁、唯一约束和每日额度检查保护持久化结果。Redis 成功是“处理中”，数据库确认后才是真正预约成功。
3. **故障可重放**：`request_id` 幂等；Worker 提交数据库后才确认 Stream；若结果不明先查数据库，明确失败再补偿 Redis。
4. **库存显示不是直接读一个表**：日期批次与结构来自 PostgreSQL，开放批次的实时占位叠加 Redis 状态。因此“处理中”能在 Worker 落库前出现。

## 5. 老师现场要求修改时，先改哪里

先问清楚“改的是**展示**、**接口返回**、**真正业务规则**，还是**数据库结构**”。只改按钮文案通常无需动后端；业务规则必须把前端、Redis、数据库服务和测试一起核对。

| 可能的现场题目 | 首先定位 | 还要同步检查 | 最快验证 |
|---|---|---|---|
| 改页面标题、提示语、颜色、间距 | `web/src/App.vue` 或 `web/src/AdminPanel.vue` 的模板；`web/src/style.css` | 是否有重复文案 | `docker compose build nginx; docker compose up -d nginx`，刷新 8080 |
| 改学生可选日期或默认日期 | `web/src/App.vue` 的日期计算、`selectServiceDate` 和 `refreshInventory` | `apps/scheduler/main.py` 生成范围；库存接口；开放模板及现有批次 | 库存生成和异步 API 测试，实际切换日期 |
| 改“已预约/已过期/处理中”的显示 | `inventory/controllers/http.py` 的 `_visible_slot_status`；`App.vue` 的 `visibleSlotStatus`/`slotLabel` | Redis 状态和 `inventory/schemas.py` 类型 | 库存/异步 API 测试 + 页面查看 |
| 改每天最多可订数或单次可选数 | `redis_reservation.py`、`reserve_slots.lua`、`sync_booking.py` | `bookings/models.py`、`users/models.py` 的检查约束、新迁移、前端限制及测试；已有 Redis 用量 | Redis、同步、异步预约及数据库约束测试 |
| 改开放时间、每时段长度或星期 | `venues/models.py`、`inventory/services/inventory.py`；管理模板数据 | 固定数据库约束、种子数据、新迁移、已生成批次不会自动回写、页面文案 | 库存服务和库存生成测试 |

| 改登录有效期/角色限制 | `shared/config.py`、`auth/security.py`、`auth/dependencies.py` | `admin/controllers/http.py` 和学生预约角色校验 | 认证、管理接口测试 |

## 6. 常见答辩问答

**为什么用 Redis 和 PostgreSQL 两套状态？** Redis 负责高并发原子占位和实时“处理中”，PostgreSQL 保存最终业务事实、关系和约束。两者之间由 Stream Worker 及失败补偿衔接。

**如果 Worker 宕机？** 未确认的 Stream 消息可被其他 Worker 重领，重复事件用 `request_id` 幂等处理；结果不明时先核对数据库。

**为什么预约请求返回处理中？** 接口完成的是 Redis 占位；Worker 落库需要时间。前端保存请求编号，随后查询 `PROCESSING/CONFIRMED/FAILED`，超时后也可继续查询。

**为什么星期掩码 127 表示每天？** 周一到周日分别占二进制 7 位，`1+2+4+8+16+32+64=127`；生成库存时在 `inventory/services/inventory.py` 按 `1 << service_date.weekday()` 判断。

**210 个库存怎么算？** 15 片场地 × 08:00 到 22:00 的 14 个 60 分钟时段 = 210。例外日期、场地停用或不同开放时间会改变实际生成数。

**为什么同一时间能订两片场地？** 当前按“时段数量”计每日额度；数据库迁移 `0006` 移除了同一用户时间排斥约束。两片不同场地是两个库存时段，仍各自只能卖一次。

**压测目前能说明什么？** Locust 页面可以展示健康接口的 HTTP 吞吐、延迟和失败率；预约核心的并发防超卖证据来自 Redis/数据库集成测试。完整预约链路的容量目标仍需另外编写带登录、库存查询、提交和结果确认的压测脚本并记录结果。
